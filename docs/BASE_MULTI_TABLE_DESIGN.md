# 多维表格多数据表迁移设计（未启用）

## 边界与数据模型

现有字段、记录、视图、自动化和事件直接绑定 Base 节点，不能仅通过前端标签模拟多数据表。保留 `nodes(kind=base)` 作为文件、分享和回收站边界，新增独立的 `bt_tables` 身份；字段、记录、视图、自动化、表单及关联均增加 `table_id`，用复合约束确保数据表属于指定 Base。旧字段、记录、视图 ID、单元格、附件归属及主字段标识保持不变；主字段唯一约束改为每个数据表独立。

## 无损迁移与混版门禁

在可验证地停止旧写实例并排空事务后，为每个既有 Base 建立稳定默认数据表，把原字段、记录、视图、表单令牌与版本、自动化和事件归入其中。迁移在事务中核对行数、引用、主字段及表单状态，失败整体回滚。旧 API 在新服务中始终映射原默认表，默认表删除后明确报错，不能悄然改指另一张表。

旧服务直接按 `base_id` 查询，会把同一 Base 的多张表混读；触发器只能阻止部分写入，不能阻止旧服务跨表读取。启用第二张表前必须验证旧服务已排空并实施数据库级版本或角色门禁；单靠前端开关、启动检查或可空列不够。旧客户端可以通过新服务的默认表适配继续读取原表。

### 可复用核心的候选兼容层（仅原型）

一种值得继续验证的路线，是将字段、记录和视图的物理表增加显式表作用域，并将旧表名保留为只展示默认作用域的可更新视图；新代码通过显式 `TableRef` 在事务中访问相同物理 schema。这样已知旧 SQL 仍只看到默认数据表，而无需复制一套字段和记录模型。在隔离 PostgreSQL 16 中，一个含作用域过滤与 `CHECK OPTION` 的简单自动可更新视图，底表使用 `BEFORE INSERT` 触发器时，已验证旧式 `INSERT … RETURNING`、`UPDATE`、`ON CONFLICT DO NOTHING`、指定冲突键的 `DO UPDATE` 和 `LOCK TABLE`；跨作用域冲突更新被 `CHECK OPTION` 拒绝。这只证明该最小原型可行，不能推广到含 `INSTEAD OF` 触发器或规则的复杂视图，也不能据此证明整个项目完整兼容或安全。

`server/internal/store/multitable_compat_test.go` 使用独立 PostgreSQL schema、实际迁移和非 owner 旧角色，实验字段、记录、视图和关联的默认作用域视图。它验证了当前旧 Store 的部分读写、关联冲突处理与锁，以及旧角色无法直接读取底表。原型还需要在旧关联写入时校验目标记录的作用域：仅过滤视图无法阻止旧代码拿已知 ID 指向新表，测试中的候选触发器会拒绝并回滚该关联。该测试没有覆盖生产角色部署、完整表归属外键、表单、事件、自动化、附件或文件级操作，因此不是开放多数据表的依据。

候选层必须为所有连接池读取和写入提供显式事务作用域；权限检查和 `(base_id, table_id)` 归属校验必须在同一事务中完成。跨表关联、反向关联和一次快照中读取多个表不能依赖单个会话变量，需显式携带源、目标表身份。旧的主字段触发器、约束、批量操作、表单令牌、自动化和事件均需逐项迁移及混版验证；冲突处理还须验证不能推断无权记录存在。旧版导出当前表与未来文件级备份/复制的语义也必须明确。

此方法只说明已知旧 SQL 通过兼容视图读取默认表，并非数据库级隔离：当前应用和迁移共享数据库账号，旧进程若直接查询底层物理表仍可读到其他表。正式上线仍需独立受限运行角色或可验证的旧实例排空与防重启门禁；不能把可被客户端设置的事务变量当作授权凭据。

建议实施分工为：① schema/store 负责无损默认表迁移、兼容视图、显式 `TableRef` 和受限角色门禁；② API 负责表归属、权限、CRUD、视图、CSV、表单、附件及关联的表作用域；③ 前端负责包含 Base 和数据表身份的路由、缓存和真实操作入口。应先完成旧 API 默认表兼容，再完成新表所有数据/权限/事件路径，验证旧实例隔离后才开放第二表；不要先开放只有部分入口可用的空壳。

## 权限、关联与表管理

每个新请求先校验 `table_id` 属于 Base，再检查账号、文件权限及当前表的数据限制；查询、导入导出、附件、表单、事件和缓存键都必须携带表身份。现有项目支持跨 Base 关联，迁移时应保留原关系并标记兼容来源，不能删除或静默改写；新建同一 Base 内跨表关联时按稳定顺序锁定两端、校验权限，并原子写入数据与事件。

表管理需要真实的新建、重命名、顺序比较写入、复制、软删除与恢复。复制须明确是否复制记录、重映射字段和记录引用，不能复制可用的公开表单令牌。表恢复不得意外重新公开已关闭链接。飞书的多维表格数据表与双向关联规则可参见[入门教程](https://www.feishu.cn/content/article/7574713887522639055)及[双向关联说明](https://www.feishu.cn/hc/zh-CN/articles/653027931590)。

## 分阶段验收

先建立无损默认表映射和旧 API 兼容测试，但在旧服务隔离及表级 CRUD、视图、事件和权限全部覆盖前，不开放多表创建。随后实现真实表切换和管理，再补复制、回收恢复、关联和表级高级权限；不能把未实现的入口画成可用按钮。

必须验证 Memory 与 PostgreSQL 的旧库迁移、原链接和表单令牌、两表同名字段隔离、恶意混搭 Base/table/record、权限撤销与隐藏列、并发创建/删除/写入、旧跨 Base 关联保留、混版门禁、重启与回滚。浏览器还需验证两个窗口中同表同步、不同表隔离及移动端操作。Base 历史版本是独立工作，不能将文档快照或事件日志当成已实现的表格历史还原。
