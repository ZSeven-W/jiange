# 文档标题一致性设计（尚未启用）

## 现状和目标

文档标题存在两份数据：协同文档中的固定标题块 `0:1` 和目录元数据 `nodes.title`。编辑正文标题后，旧客户端通过独立的、延迟的 PATCH 写目录；侧栏重命名仅写目录。网络离线、并发编辑、重排请求、关闭页面和历史还原都可能使两者分叉。目录中的旧值也可能是用户最后一次侧栏改名，不能推断哪一份才是用户想保留的内容。

目标是把固定标题块作为新的协同权威，目录标题作为同序号的服务端投影；明确保留并提供用户恢复旧分叉两侧的途径。Base 使用独立模型，不纳入本设计。

## 写入和广播

1. 普通协同操作和历史还原都必须在与追加操作相同的存储事务内计算投影。PostgreSQL 先锁 `doc_heads`，在该事务读取不超过 head 的最新快照及连续操作日志，再只应用实际入库且未重复的操作，更新标题投影、head 并发出事务内通知；Memory 使用同一把锁实现等价语义。多实例不能直接使用房间中可能落后的内存标题。
2. 物化过程应校验快照、连续序号、单条日志恰好一项操作及无待解决依赖。`0:1` 必须是可见的 title 块；缺失、删除或损坏时不能投影隐藏文字，也不能静默覆盖已有目录值。需要安全的错误和恢复路径。
   现有快照不保留全部已见操作 ID，因此物化过程无法单独证明跨快照没有操作身份冲突；必须依靠完整的数据库唯一约束，并解决数据库回滚导致历史身份及序号重用的问题。
3. 原文完整保留，不对协同标题裁剪、截断或默默归一化。当前侧栏输入的 200 码点限制与正文输入不同，统一限制之前必须明确对离线及旧客户端的兼容策略，不能拒绝已产生的草稿或截断现有文字。
   PostgreSQL `text` 不能保存 NUL 字符；旧标题或未确认草稿含 NUL 时，需要显式保留可导出的原内容并给出恢复路径，不能丢弃或伪装同步成功。对于超出 JavaScript 安全整数范围的操作 ID 及字符跨度，同样需要拒绝不兼容投影并保留恢复信息。
4. 新的显式重命名先读取用户可见的标题与准确 head，确认后按该 head 生成 CRDT 操作，并在提交事务内重验会话、权限和 head；若 head 改变则返回冲突，显示最新值并由用户决定，不能静默重试整段覆盖。离线尚未提交的并发输入可能仍按 CRDT 规则合并，需在产品中说明并测试。
5. 投影及操作提交后继续通过既有通知和房间追平机制广播；断线或失败不能提前 ACK。跨实例并发、重复批次、混合正文与标题操作、撤权、事务回滚及重连须有端到端测试。
6. 在数据库 head 锁内物化时，应避免为提取标题而渲染整篇文档，提供能检查标题块可见性及类型的定向读取方式，并验证大文档、高并发场景下的锁等待和内存开销。
7. 替换整段标题时，新插入操作必须引用不会被 GC 移除的永久根锚点。仅按 head 校验不足：同一 head 的压缩快照可能在生成操作后提交，并移除原快照中的已删除叶子。服务端生成操作应避免创建长期未确认的普通客户端副本，以免阻塞 GC 水位。

## 历史数据与兼容

- 上线前先按文档记录旧目录标题、当前协同标题、对应 head 和时间；当二者不一致时持久保存双方及文档标识，提供用户可见的比较、选择和恢复，不直接把一方当成历史事实。记录操作必须和 head 锁或 CAS 配合，避免在扫描与写入之间丢掉新的更改。迁移要支持分批、重试、中断续跑及损坏数据报告。
- 旧客户端的延迟 PATCH 与用户主动重命名在原协议中不可区分。新客户端应停止把本地编辑结果作为无条件 PATCH 镜像，使用显式重命名接口；服务端对旧版文档标题 PATCH 明确返回升级提示，而非用陈旧值覆盖协同内容。部署必须有版本门禁和升级提示，避免旧版静默失败。Base 的 PATCH 不变。
- 仅靠当前页面的编辑锁无法挡住已卸载页面发出的迟到 PATCH。提交结果未知时，仅重新读取一次标题也不能证明原请求不会稍后提交；需要持久幂等操作状态与可串行取消机制，并同时约束旧 PATCH，才能安全解除写入屏障。
- 历史版本可能删除原固定标题块或创建不同 ID 的标题块。此类还原不能假装完成：应在提交前拒绝并保留当前内容，或先设计经过验证的安全迁移；还原成功也需在同一事务更新标题投影。

## 候选接口

- `GET /api/docs/{id}/title-state`：授权后返回 `{title, head}`；若存在历史分叉还需返回可供恢复的冲突信息或引用。
- `POST /api/docs/{id}/rename`：接收 `{title, expectedHead}`；成功返回实际标题和新 head；期间有并发变化返回 `409 title_conflict`，不提交部分修改。
- 旧文档标题 PATCH 返回 `409 upgrade_required`；对包含其他字段的旧请求应在任何字段生效前整体拒绝。

以上接口只是候选契约，目前未启用。只有原子投影、冲突留存及恢复界面、兼容门禁和端到端验证全部完成后才能替换现有行为。

## 可恢复的增量投影方案（待实现）

`ReadTitleSnapshot` 目前限制快照和操作总量，适合有界的只读检查，不能在每次写入时用于重放整篇文档：这会把大文档变成不可编辑文档，并使数据库头锁持有时间随正文大小增长。下面的索引只是一项候选实现；在投影、冲突恢复、协议门禁和部署门禁全部完成前，不切换任何用户的写入行为。

### 索引内容与增量更新

- 为每个已切换的文档持久化与同步协议相同的 `(epoch, seq)` 检查点。索引需要保存**所有块**的身份、父节点、位置寄存器版本和删除状态，以及固定标题块 `0:1` 的类型寄存器与完整字符 CRDT（包括仍可能被引用的已删除字符）。只保留标题文字本身不足以处理并发插入、删除、重试和离线合并。
- 正文块的文字和格式不必复制进标题索引；但任意块的创建、移动和删除都可能改变标题的祖先链或可见性，必须增量处理。即使标题块本身没有操作，其所在祖先被删除、父块后来创建或块树出现环时，显示结果也可能变化。标题块的类型修改同样必须处理。可见性和环的语义必须与 `collab.Doc` 的真实视图一致，而不是另行猜测。
- 直接从 `doc_ops` 有序重放时，现阶段仓库没有生产删除该表的路径，可以从序号 1 分页重建而不加载完整正文或受 `ReadTitleSnapshot` 的 2 MiB / 1 万操作上限约束。必须逐行校验序号连续、单行单操作、操作身份及内容；已有日志身份冲突或其他无法证明正确的历史应保留原始数据并进入待恢复状态。仅检查标题相关操作不能证明正文依赖正确，不能把该投影器当作完整 CRDT 验证器。
- 快照流式提取完整块拓扑和标题字符可作为加速路径；解析器必须验证格式、边界与压缩数据，并能在缺失、损坏或不可信时回退到保留的日志。快照可能已压缩掉 tombstone，投影检查点和随后的操作必须采用一致的 GC 语义。以后若引入日志删除，只有在确认投影检查点、身份账本及恢复所需的日志均已安全持久化后才可回收。
- 普通操作和历史还原在同一 `doc_heads` 锁与事务中完成身份检查、实际插入、索引增量、检查点、目录显示值、head 更新和通知；重复操作只核验、不得重复应用。新建和复制也必须在创建事务中初始化相同索引；Memory 实现需有同等原子性。多实例不得以某个房间的内存标题代替事务内结果。
- 索引应允许不阻塞正常编辑的重建。实际实现需量化标题 CRDT 大小、单次事务和锁等待；对正文规模较大的文档，正常追加的锁内成本不能随整篇正文体积线性增加。标题本身极长时应保留完整内容，显示和搜索可以有明确标记的独立展示策略，但不能把展示替代值当成原文写回。

### 在线迁移与异常恢复

1. 先部署兼容的服务、索引表、身份账本及完整性检查，但不更改旧文档的写入路径。后台以有限并发、可中断、可续跑的方式按文档重放，记录读取的 epoch、连续序号和进度；新写入期间继续分批追尾，不能在文档头锁内全量重放。
2. 追平后，在短事务中锁住文档 head，核实 epoch 和索引所对应的序号，处理可控的最后增量；若发生代际变化或追尾超出事务预算，回到后台继续追平。事务内原子保存旧目录标题、准确的 CRDT 原值、head 和时间，再标记该文档的投影已启用。二者不同也先保存双方，不以任何一侧自动覆盖另一侧作为历史事实。
3. 标题不存在、隐藏、类型异常、编码无法表示或历史损坏时保留目录原值、CRDT 原始数据及诊断信息，并提供用户可见的比较、导出和显式恢复。不能将不可见标题文字作为目录标题；也不能把一个损坏文档的投影异常扩大为所有大文档正文无法编辑。异常文档应保留明确的状态与安全的编辑、导出和恢复路径，完成设计和测试后才能启用切换。
4. PostgreSQL `text` 无法保存 NUL。完整权威值需要可无损存储的形式，例如 UTF-8 字节；单独标记不可直接展示的值，显示层的替代文本不得参与自动重命名或覆盖。长标题、NUL 和其他历史异常均需覆盖迁移、搜索、复制、导出及恢复测试。
5. 新的显式重命名/恢复使用请求 ID、期望 epoch/head、会话和权限校验；提交、结果持久化、查询状态与取消之间要有可串行的结果，使超时或页面重载后能够区分已提交、未提交和取消，而不是凭一次读取推测请求不会迟到。不得静默重试并覆盖用户已看到的并发修改。

### 协议及部署门禁

- 旧编辑器的延迟 PATCH 和主动重命名无法区分；旧同步协议也没有可验证的代际证明。切换后的文档必须同时约束旧标题 PATCH 和旧协同写入，并为旧客户端提供升级与本地草稿恢复提示；只在新 API 拒绝 PATCH 无法约束仍在运行的旧服务。
- 若新旧实例共用可以直接写表的高权数据库凭据，事务局部变量或其他同角色可自行设置的标志**不是安全边界**。部署需要可验证地排空旧实例并撤销旧凭据，或者改为受限应用角色、通过受控的数据库写入过程执行新协议，同时禁止绕过；只做版本号判断或只增加触发器不等同于完成此门禁。
- 操作身份校验、同步协议代际和标题检查点必须共享同一序列化边界。数据库备份回滚后的代际证明依赖独立于该备份的可信状态或等价的恢复流程；不能仅凭回滚数据库中一起回滚的计数器断言历史没有变化。需与协同协议升级一同设计和验证。

### 上线验收

以随机生成的块树、祖先移动/删除/重建、环、标题字符并发编辑、重复及乱序操作，与完整 `collab.Doc` 的可见标题逐序号比对；另测重启、重建、恢复、GC、事务回滚、多实例竞争、撤权、提交结果未知及数据库回滚。用真实大正文、高频并发写入和极长标题测量迁移吞吐、内存、锁等待及前台编辑延迟；只有满足预先约定的性能和恢复目标，且旧服务写入门禁、冲突保留和用户恢复链路都有端到端证据，才逐批开启。
