## 10. 第三轮：历史操作人 / 评论回复·@·解决 / 多选与人员默认值（2026-11-09 夜）

截图：`docs/screenshots/r5-history.jpg`（历史带操作人）、`r5-comments.jpg`（回复 + @ 提及 + 已解决）、`r5-mention-picker.jpg`（@ 成员选择）、`r5-default-multi.jpg`、`r5-default-person.jpg`。

- **历史操作人**：迁移 0045 给 `bt_events` 加 `actor_id`（引用 users，删除用户置空）与 `actor_kind`。登录请求在 `requireUser` 中把当前用户放进 context（`store.WithActor`），所有带记录快照的写入路径都写入操作人：单元格/记录增删改（MutateRecordGuarded，含批量删除逐条调用）、看板拖卡、日期比较写入、字段类型转换引起的记录更新、通用 AppendBtEvent；匿名公开表单提交写 `actor_kind='form'`。历史接口返回 `actor {kind,id,name}`（姓名取工作区成员与直接分享成员，不含邮箱）；界面显示头像 +「沈墨 修改了记录」，表单为「表单提交 创建了记录」；迁移前的旧事件回退为「修改了记录」，旧的创建事件用记录创建者。
- **记录评论**：一层回复（父评论必须是同一记录的根评论）；`@` 弹出成员选择（工作区成员 + 分享成员，↑↓/Enter/Tab 选择），正文中的 @姓名 渲染为蓝色标签；被 @ 的人收到通知（复用文档评论的 mention/reply/resolve 通知），但服务端只保留**当前能看到这条记录**的人，锁定视图下看不到该记录的人不会收到预览。解决 / 重新打开，已解决的讨论默认收起，点「显示已解决 N」展开。新增记录级 `PATCH/DELETE /records/{rid}/comments/{cid}`；通用 `/api/docs/{id}/comments/{cid}` 的修改/删除对记录评论返回 404（修补了上一轮遗留：之前可绕过记录可见性去解决/查看记录评论）。
- **默认值**：多选字段为可多选的选项标签（按选项颜色），人员字段为成员下拉（与人员单元格编辑器同一成员列表）。

本轮仍未做：回复通知会发给父评论作者，即使其后来失去该记录的可见性（预览仍可能送达）；评论无表情回应、编辑 UI、附件；人员默认值只能选 1 人；历史仍不含删除事件（删除后记录不可打开）。
