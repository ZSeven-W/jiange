# 多维表格事件与快照协议：迁移设计（未启用）

## 现状与目标

当前 `bt_events.id` 是数据库全局自增值，同一多维表格的相邻事件可能因其他表的写入或事务回滚而跳号。客户端将事件作为重新读取授权快照的提示，并在前台定期重取；`GET /api/bases/{id}` 的主要数据和 `head` 已放入一致性快照，但筛选端点及输出前权限变化仍有独立边界。现有协议提供最终收敛兜底，不是可证明无缺口的实时协议。

升级目标是：每个 Base 的提交按持久 epoch 和连续序号识别；数据、事件和序号同事务提交；返回给客户端的所有授权数据与该序号来自同一读取快照；重连、丢帧、回滚和旧客户端不得把不兼容的历史当成可安全重放的增量。实时帧仍不能包含调用者无权查看的原始行、字段或关联值。

## 数据模型与事务

1. 保留现有 `bt_events.id` 作为旧版失效提示的游标。新增按 Base 的持久 head（Base ID、随机 epoch、当前 seq）以及事件的 epoch/seq，约束 `(base_id, epoch, seq)` 唯一；旧日志不应被解释为新 epoch 的连续历史。
2. 所有生产写入必须在同一事务内按 Base ID 的确定顺序锁定涉及的 Base 与 head，修改记录、字段、视图、双向关联、表单和导入数据后递增对应 head 并追加事件。回滚不能推进 head；跨表写入必须为每个受影响 Base 记录事件。自动化配置与表单发布状态是否需实时投影，也应明确纳入，而不是默认忽略。
3. 新建 Base 的初始字段、视图和记录与 head 初始化须同事务完成，或以不会产生重复 epoch 的方式安全地懒初始化。被删除或恢复的 Base 不能让旧客户端把新历史误认为原历史；数据库回滚后也须通过外部恢复流程更换 epoch，单靠数据库内旧 epoch 无法检测自身回滚。
4. Memory 实现使用同一互斥锁提交数据、每 Base head 和事件，并对返回的映射、切片和原始 JSON 做深拷贝。不得保留跨 Base 共享计数作为连续序号。

## 快照和网络协议

1. 新快照必须在一个 PostgreSQL `REPEATABLE READ READ ONLY` 事务中读取 Base 元数据、字段、视图、授权记录、关联/反向关联、目标表权限及 head；Memory 在同一锁内构造等价的不可变快照。不得在这些查询之间重新从连接池读取不同版本。对目标表按实际引用 ID 批量授权，达到限制时明确返回不完整错误，而不是扩大或静默截断访问范围。
2. 快照响应提供明确的协议版本、epoch 和 seq。新客户端只有在当前账号、Base 和 epoch 均匹配、上次快照成功且所有增量连续时才可使用该游标；epoch 缺失/变化、seq 回退、缺口、连接关闭或出站队列溢出均丢弃游标并重新读取授权快照。事件只传失效提示或经过逐接收者授权的投影，不能恢复原始单元格广播。
3. 授权快照一致不等于撤权与网络发送严格线性化。输出前还需重新校验原会话、源和目标访问范围，明确剩余的读取至发送窗口；失败不得使用旧缓存冒充授权结果。

## 旧实例与迁移门禁

- 已运行的旧服务可能先提交 Base 数据，再在独立事务追加旧事件。仅给 `bt_events` 新增序号列或启动时检查版本，不能阻止它写出没有同事务事件的数据。上线前必须通过数据库级写栅栏阻止旧写端，或使用可验证的维护流程停止并排空所有旧写实例和在途事务；仅依赖部署文档而不验证旧写端已停不是安全门禁。
- 数据库级栅栏需覆盖所有影响快照的 Base 表及级联路径，并让新版每条合法写入在同事务声明协议版本。应使用受限应用数据库角色防止普通运行时绕过触发器；迁移、清理和恢复流程需有明确且受控的例外。旧版本在栅栏启用后必须明确失败，不得先成功写数据再失败写事件。
- 在门禁生效且旧事务排空后，以当前已提交数据为新 epoch 的基线，初始化 seq；保留旧日志以供旧协议兼容或审计，不将旧全局 ID 直接当作新 seq。旧客户端应继续使用安全的授权快照失效提示或明确要求升级，不能把旧游标传给新协议使用。
- 灰度和回滚方案必须覆盖多实例混版、迁移期间写入、数据库恢复、后台自动化、匿名表单与客户端长期离线。未经这些门禁和回归，不能打开按 epoch/seq 的增量模式，也不能移除现有前台刷新兜底。

## 代码入口盘点与切换顺序

当前事务内追加事件的路径分散在字段、记录和双向关联、日期比较写入、CSV 导入、公开表单及视图管理的 Store 实现；字段排序和表单配置还会复用视图刷新事件。新建 Base 的初始字段、视图与记录在一个事务中创建，但目前没有独立的 Base 事件头。内存实现虽然按 Base 保存事件，序号计数器仍是全局值。

旧的 `AddField`、`UpdateField`、`DeleteField`、`AddRecord`、`SetCells`、`MoveRecord`、`DeleteRecord`、`AddRecordsBulk`、`MapFieldCells`、`SetLinks`、视图增删改和 `AppendBtEvent` 仍作为 Store 方法存在；旧服务可能在独立事务中调用它们。`importCSVLegacy` 目前仅用于测试，不能据其未注册推断旧服务不会调用低层写方法。自动化配置增删改目前走独立接口且不产生 Base 事件，其订阅与权限语义必须单独定义。

建议按以下顺序上线，而非让 `migrate.Up` 自动切换运行协议：

1. 先发布兼容版，保留旧 `bt_events.id` 和 `reload` 协议；补齐所有生产写路径的数据与失效事件同事务、跨 Base 按 ID 排序锁定，以及同一快照读取新旧事件头。此阶段仍使用轮询。
2. 以具备数据库管理权限的独立迁移步骤安装默认关闭的协议门禁。门禁需覆盖 `base_fields`、`base_records`、`bt_views`、`bt_links`、表单及自动化相关表，以及影响 Base 可见性或内容的节点、分享、成员和级联路径；不能仅保护 `bt_events`。应用运行角色不得能禁用触发器或自授绕过权限。仅可设置的会话变量或 `application_name` 不能证明写端版本，也不能单独作为安全栅栏。
3. 管理员停止入口、排空旧实例和在途事务，启用门禁后验证旧应用角色的每种写路径均在修改前失败；验证步骤或权限不足时保持旧协议及轮询，不进入 v2。切换事务中以当前已提交数据为新 epoch 基线，逐 Base 初始化头；数据库恢复或回滚后须通过外部恢复流程重新生成 epoch。
4. 新服务器与客户端完成版本协商后才读取/发送 v2 游标；保留 v1 安全失效提示给旧客户端。出现缺少 epoch、头回退、数据或权限重验失败、连接关闭或队列溢出时只重取授权快照，不猜测或跳过事件。切换与回滚均须验证跨实例、旧实例重连和自动化任务。

前台定期授权刷新与事件失效提示是过渡措施：它们只能在网络恢复且写入停止后趋于最新，不能证明实时顺序、数据库恢复身份或瞬时撤权。

## 必须验证

- 两个 Base 交错写入时各自序号连续；同一 Base 的并发事务、回滚和跨实例提交顺序与数据库一致。
- 读取快照期间写入、跨表关联权限变化、节点回收/恢复、角色撤销及源/目标表受限时，不返回旧数据搭配新游标，也不暴露未授权数据。
- 多页重放、慢连接队列溢出、错误与超时、旧客户端、断线长期离线、旧实例写入尝试、迁移和恢复后的 epoch 不匹配均触发安全重读或明确失败。
- 测量批量导入、关联写入和大房间的延迟、数据库连接占用与锁等待，避免把按事件逐行锁定引入的性能风险误作已验收。
